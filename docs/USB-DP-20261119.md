# Uke USB host and DisplayPort extended desktop

## Device observations

On earlier images the device owner confirmed USB keyboard and mouse input through a dock, Files opening, and a portable drive mounting and transferring data at an expected speed. The drive took about one minute to appear in Files. A later image showed 215 GB in About. That capacity replaces the earlier 6 GB figure based on the SystemOS disk. The correction derives capacity from the mounted Data volume. These observations do not cover every dock, drive or Files filesystem.

Extended mode with the full-damage fix (`vendor_boot` SHA-256 `9a0fc473220661d6c6a350ad3563da520ef7e060af11dab8801b36784017c7d9`) eliminated the reported black blocks and flicker. The matched log recorded 2560×1440 at 60 Hz on the wire and a 1920×1080-point iPadOS workspace at 2×, composed into a 3840×2160 `b3a8` XR10 surface. The CPU copy path presented 12.15–12.99 new frames per second in four complete sessions. The median preparation time was 73.8 ms across 26 samples, with 20.9 ms for source cache synchronization and 51.3 ms for conversion and scaling.

## XR10 direct scanout candidate

`uke-dp-xr10=1` enables the native secondary display route. The internal left half moves to DMA1 via CTL0 while the right half stays on VIG1. The external route uses VIG0, LM2, PP2, CTL2 and INTF0 on DPTX0. VIG0 reads the original 3840×2160 XR10 color plane through the display IOMMU and scales it to 2560×1440. The 10-bit CSC maps XR10 code values to SDR. Only the required color pages are mapped. The producer fence and CTL latch protect buffer handoff, and a buffer remains pinned when retirement cannot be confirmed.

The OEM DRM atomic test accepted DMA1 in place of VIG0 on the internal left half and separately accepted a 4K XR30 scaling plane on VIG0. Recovery observed DP HPD but exposed no modes, so it did not validate the complete two-output combination. The pinned [SM7675 mainline catalog](https://github.com/MCC45TR/senemos-uke-kernel-mainline/blob/6719b05ea34725031a4a0b888fa7b57b5cd49839/src/display/dpu_10_1_sm7675.h) identifies the same pipe and interface roles.

The kernel and payload build passed, with 984 bytes of kernel arguments and no new missing prelink bindings. Host checks passed for UCSI, EDID and HBR2 link policy, DPU timing, full-frame geometry, producer fence deferral, IOMMU bounds and lifetime, and the panel-DMA1/XR10 contract. The packaged `vendor_boot` round trip passed. The candidate was assembled from the working trees before publication, with the source revisions pinned in `feeds.toml` and the companion UniXNU checkout.

- `vendor_boot` SHA-256 `c0a6f7ec931519393520dfe82e15e650d79c3eaec18a045eb0302a081068e19a`
- Kernel SHA-256 `833c586224fb0b4e564f5a5577dae0d50c8dd92c1222a545c9e1cd6fa79ca910`
- `boot_a`, `vendor_boot_a`, `boot_b`, and `vendor_boot_b` writes succeeded. `set_active a` and `reboot` succeeded.

The first XR10 candidate produced the native extended desktop and a gray internal panel. The next revision moved the handoff to HPD, but the same gray output still occurred while the external link was active. Later device observations are recorded below.

## Split-panel handoff and device acceptance

The OEM DRM commit at the same layer stage programs VIG1 as the right source and sets an opaque stage on both layer mixers. The Uke handoff now commits both SSPPs and mixers on CTL0, retains the active panel buffer, and returns it to VIG0 after CTL2 stops. The device owner confirmed that both screens displayed correctly on vendor_boot `93c30b07eb1bab788eff6370f366694dca17446be738cd8ac14eab52538043a7`. All four panel pixel signatures matched before and after DMA1 acquired the same frame. The log showed the two panel interfaces scanning at 120 Hz and DP at 60 Hz.

The user reported uneven motion on both outputs. The external presentation rate fell from 35.5 to 22.0 frames/s in the sampled intervals. The slower interval's median XR10 preparation was 31 microseconds, GPU fence wait was 30.8 ms, and latch wait was 10.0 ms. This trace lacks continuous per-screen presentation counters and per-IOSurface GPU completion data.

The next candidate leaves routine mode information and failure reports enabled. `uke-dp-debug=1` opts into periodic timing, pixel signatures and AUX receiver diagnostics. The normal build leaves the argument unset. The Wi-Fi recovery image `b92e39d1aeade0b687a3ce1793f0a2bb631aa405e1664e2ee5361ae65c68dfaf` carries the same kernel, ADT and boot arguments as that quiet DP build. The owner accepted the Wi-Fi recovery in device testing. A separate dual-display frame-time comparison on the quiet build remains open.
